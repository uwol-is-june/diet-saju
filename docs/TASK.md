## 사용자 작업 (개발과 병행 가능)

대시보드·계정 작업이라 코드로 처리할 수 없다. 둘 다 **링크를 남에게 보내기 전에** 끝내야 한다.
개발을 막지는 않으므로 아래 개발 순서와 병행한다.

### [TASK-18] 프로덕션 모델 교체 · **(H)** · ⬜ 대기

코드 기본값은 이미 `gemini-3.5-flash-lite` 다. 프로덕션은 Vercel 환경변수 `GEMINI_MODEL` 이
`gemini-3.5-flash` 로 덮어쓰고 있어 **하루 20건 · 첫 글자 8.5초**로 돌고 있다.
쿼터가 25배 차이나고, 응답도 함수 타임아웃(30초)에 가까워진다.

CLI 계정(`seojunincar-8503`)과 실제 배포 프로젝트의 계정이 달라 코드에서 처리할 수 없다.

- [ ] Vercel > diet-saju > Settings > Environment Variables 에서
      `GEMINI_MODEL` 을 `gemini-3.5-flash-lite` 로 수정 (Production/Preview/Development)
- [ ] Redeploy (환경변수는 재배포해야 반영된다)
- [ ] `POST /api/saju` 응답의 `model` 필드가 `gemini-3.5-flash-lite` 인지 확인
- [ ] 첫 글자가 3초 이내로 떨어졌는지 확인 (로컬 기준 약 1.3초)
- [ ] 잘못 생성된 빈 Vercel 프로젝트 삭제 — `seojunincar-8503s-projects` 스코프의
      `diet-saju`(Production URL 이 `--`, 배포 이력 0건). 실제 서비스 프로젝트와 다른 계정이다

→ 완료 기준: 프로덕션이 lite 로 돌고 첫 글자가 3초 이내다. 일일 한도 500건.

### [TASK-19] 문의 연락처 확정 · **(H)** · ⬜ 대기

`app/privacy/page.tsx` 9항의 문의 창구가 `(운영자 연락처 준비 중)` 자리표시자로 남아 있다.
개인정보 처리방침에 연락 수단이 없으면 고지 요건을 갖추지 못한다.

- [ ] 공개할 이메일(또는 폼) 결정 — 개인 메일 노출을 피하려면 별도 주소 권장
- [ ] privacy 페이지 9항 교체
- [ ] 서비스를 실제로 홍보할 단계가 되면 문구 전문가 검토 여부 판단

→ 완료 기준: 개인정보 처리방침에 실제 연락 가능한 창구가 적혀 있다.

# 개발 순서

## 1. [TASK-11] UI/UX 다듬기 · **(H)** · ⬜ 대기

**먼저 하는 이유**: 값이 싸고 즉시 보인다. 컬러 교체와 스트리밍 도입 직후라 거친 곳이
남아 있을 가능성이 높다. 특히 스트리밍이 시작될 때 원국이 화면 밖에 있으면 "아무 일도
안 일어난 것"처럼 보인다 — 지금 구조에서 실제로 그럴 수 있다.

- [ ] 결과 영역으로 자동 스크롤 (스트리밍 시작 시 원국이 화면 밖일 수 있다)
- [ ] 모바일 폼 레이아웃 점검 (생년월일 입력, iOS date picker)
- [ ] 긴 대운 표의 가로 스크롤이 모바일에서 자연스러운지 확인
- [ ] 접근성: 라벨-입력 연결, 포커스 링 가시성
      (대비비는 컬러 토큰 테스트로 고정됨, `aria-live` 는 스트리밍 도입 때 적용됨)

→ 완료 기준: 모바일에서 입력~결과까지 걸림 없이 진행된다.

## 2. [TASK-14] 체질·다이어트 리딩 심화 · **(O)** · ⬜ 대기

**이 순서인 이유**: 저장소 이름의 근거가 되는 차별화 지점이고, 선행 태스크(만세력 정확도·
해석 근거 확장)가 끝나 해금됐다. 그리고 **다음 태스크(구조화 출력)보다 먼저** 해야 한다 —
내용이 확정되기 전에 형식을 고정하면 두 번 고친다.

`종합` 유형은 그대로 두고 `diet` 유형만 심화한다 (두 유형 유지가 확정 사항).

- [ ] 오행 균형·왕상휴수사·신강신약 → 체질 경향 매핑 규칙표를 코드로 작성
      (LLM 즉흥 판단 금지. `lib/saju/analysis.ts` 의 고전/관례 구분 방식을 따를 것)
- [ ] 식습관·운동 제안을 규칙표에서 뽑아 프롬프트에 근거로 제공
- [ ] 매핑 규칙을 테스트로 고정 (`lib/saju/*.test.ts` 방식)
- [ ] 의학적 주장으로 읽히지 않는 표현 가이드 확정 — `app/disclaimer/page.tsx` 문구와 정합

→ 완료 기준: 같은 사주에 항상 같은 체질 판정이 나온다 (판정은 결정론적, 서술만 LLM).

## 3. [TASK-06] 프롬프트 고도화 + 구조화 출력 · **(O)** · ⬜ 대기

**이 순서인 이유**: 내용(TASK-14)이 굳은 뒤에 형식을 정해야 재작업이 없다. 또 풀이가
길고 복잡해질수록 구조화의 이득이 커진다.

**주의**: 스트리밍과 충돌한다. JSON 구조화 출력은 완성 전까지 파싱이 불가능해 점진 렌더가
깨진다. 지금 첫 글자가 약 1.3초에 보이는 것을 포기할 만한 이득인지 **먼저 판단**해야 하고,
그 판단 결과에 따라 이 태스크가 취소될 수도 있다.

- [ ] 스트리밍 유지 여부 결정 (섹션별 스트리밍 vs 완성 후 일괄 vs 구조화 포기)
- [ ] 마크다운 자유 서술 → `responseMimeType: "application/json"` + `responseSchema`
- [ ] 섹션별 렌더 컴포넌트 (요약 카드 / 상세 아코디언)
- [ ] 유형별 프롬프트 분리 정리 — 공통 지침과 유형별 섹션이 지금 한 파일에 섞여 있다
- [ ] 프롬프트 인젝션 테스트: 이름 칸에 지시문을 넣어도 무시되는지 확인
- [ ] 동일 입력 3회 실행 일관성 확인, `temperature` 조정

→ 완료 기준: 응답이 항상 같은 스키마로 오고, 파싱 실패 시 폴백이 동작한다.

## 4. [TASK-13] 관측과 에러 추적 · **(S)** · ⬜ 대기

**이 순서인 이유**: 다음 태스크(결과 공유)로 사람이 들어오기 시작하면 실패를 볼 눈이
있어야 한다. 공유를 열고 나서 붙이면 초기 문제를 놓친다.

- [ ] Vercel Analytics 연결
- [ ] 서버 에러 집계(Sentry 등) — **생년월일·API 키 스크러빙 설정 필수**
      (개인정보 처리방침이 "로그에도 기록하지 않는다" 고 약속하고 있다)
- [ ] Gemini 실패율 / 429 발생률 / 첫 글자까지 걸린 시간 지표화
- [ ] **상태 코드만 세지 말 것** — Gemini 실패는 200 안의 `error` 이벤트로 나간다.
      이걸 빼면 실패율이 0 으로 보인다

→ 완료 기준: 쿼터 소진·생성 실패가 대시보드에서 보인다.

## 5. [TASK-10] 결과 공유 · **(S)** · ⬜ 대기

**이 순서인 이유**: 위 네 개가 끝나야 공유할 가치가 있는 결과가 된다. 오행 배지·브랜드
색은 `app/globals.css` 의 시맨틱 토큰을 그대로 쓴다 (컬러 시스템 완료됨).

- [ ] 동적 OG 이미지 (`next/og`) — 사주팔자 4기둥 + 오행 배지
- [ ] 이미지로 저장 / 링크 복사 버튼
- [ ] 결과 영구 링크 (`/r/[id]`) 도입 여부 결정
      **주의**: 영구 링크는 결과를 서버에 저장한다는 뜻이고, 그러면
      `app/privacy/page.tsx` 의 "저장하지 않습니다" 가 거짓이 된다. 도입하면 3항(보관 기간)을
      같은 커밋에서 고칠 것. 생년월일은 링크에 노출하지 않는다.

→ 완료 기준: 카카오톡·인스타에 붙였을 때 카드가 제대로 뜬다.

## 6. [TASK-08] 결과 캐싱 · **(S)** · ⬜ 대기

**이 순서인 이유**: 캐시 키에 프롬프트 버전이 들어가므로 프롬프트가 안정된 뒤(TASK-06 이후)에
해야 한다. 그리고 사주는 입력이 겹칠 일이 적어 효과가 제한적이고, 쿼터가 500건/일로 올라가
급하지 않다.

- [ ] 캐시 키 = 해시(생년월일시 + 성별 + 양음력 + 보정 옵션 + readingType + 모델 + 프롬프트 버전 + 세운 기준연도)
- [ ] 저장소 선정 (Vercel KV / Upstash Redis)
- [ ] 생년월일 원문을 키에 쓰지 않는다 (해시만 저장)
- [ ] TTL 및 프롬프트 버전 변경 시 무효화 전략
- [ ] **`app/privacy/page.tsx` 3항(보관 기간) 갱신** — 캐싱은 "저장하지 않습니다" 를 무효화한다

→ 완료 기준: 같은 입력 재요청이 LLM 을 호출하지 않는다.

## 7. [TASK-09] 레이트 리밋 영속화 · **(S)** · ⬜ 대기

**이 순서인 이유**: 트래픽이나 남용이 실제로 생긴 뒤에 의미가 있다. 현재 인메모리라
서버리스 인스턴스마다 카운터가 분리된다 = 전역 한도가 아니다.

- [ ] Upstash Redis 기반 슬라이딩 윈도우로 교체
- [ ] IP + (선택) 세션 기준 이중 한도
- [ ] 429 응답에 `Retry-After` 유지
- [ ] IP 보관 방식이 바뀌면 `app/privacy/page.tsx` 3항 갱신 (현재 "메모리에 최대 1분")

→ 완료 기준: 인스턴스가 여러 개여도 분당 한도가 전역으로 지켜진다.

## 8. [TASK-17] 무료 등급 쿼터 폴백 · **(S)** · ⏸ 보류

**보류 이유**: `gemini-3.5-flash-lite` 로 옮겨 500 RPD 를 확보했다(기존 20 RPD).
일일 사용량이 여기 근접하기 시작하면 착수한다. 한도표와 근거는 CLAUDE.md 참고.

- [x] 후보 모델 실제 한도 확인 — Lite 계열만 500 RPD, 나머지 Flash 는 20 RPD
- [x] 모델 교체 — 기본값을 `gemini-3.5-flash-lite` 로 (품질 3건 대조 후 결정)
- [x] 일일 소진 문구 분리 — `quotaId` 의 `PerDay` 로 판별해 "내일 다시" 안내
- [ ] 폴백 체인: 주 모델 429(PerDay) → 다른 모델로 자동 재시도
      (쿼터가 모델별로 분리되므로 일일 용량이 합산된다)
- [ ] 서버에서 일일 사용량 카운트 → 소진 임박 시 조기 안내
- [ ] `RATE_LIMIT_PER_MINUTE` 재검토 (현재 5, 모델 RPM 은 15)

→ 완료 기준: 하루 몇 건까지 감당되는지 수치로 알고, 소진 시 문구가 정확하다.

## 9. [TASK-15] 리딩 타입 추가 · **(S)** · ⬜ 대기

**마지막인 이유**: 기존 두 유형이 충분히 좋아진 뒤에 늘리는 것이 맞다. 지금 늘리면
품질이 낮은 유형이 세 개가 된다.

- [ ] 올해 운세 / 궁합 / 직업 적성 중 우선순위 결정
- [ ] `readingType` 확장이 스키마·프롬프트·UI·캐시 키에 일관 반영되는지 확인
- [ ] 궁합을 넣으면 입력이 2인분이 된다 → 개인정보 처리방침 1항(처리하는 정보) 갱신
