### [TASK-33] 삼합·방합을 세력 판정에 반영 · **(O)** · ⏸ 보류

TASK-32 와 같은 사례에서 확인된 두 번째 누락. `1999-12-09 22:12` 은 지지가
**해(亥) · 묘(卯) · 미(未)** 로 **삼합 목국(木局)** 을 온전히 이룬다 — 지지 4개 중
3개이고 왕지 묘까지 갖췄다. 삼합을 보는 앱에서는 이 세 글자가 묶여 목으로 작동하므로
일간 을목이 자기 오행 덩어리 위에 앉은 형국이 되고, 신약이 나올 수가 없다.
지금 코드에는 합충 로직이 **전혀 없다.**

**보류 이유**: 성립 조건을 우리가 정해야 해서 "우리 관례" 가 크게 는다 — 합화(合化)
인정 여부, 글자 사이 거리, 반합 처리, 쟁합·투합, 그리고 월령이 국의 오행이 아닐 때
(이 사례가 그렇다 — 월지가 자수다) 화(化)를 어디까지 볼 것인가. `CLAUDE.md` 의
"고전 규칙과 우리 관례를 섞지 말 것" 에 정면으로 걸린다.

**TASK-32(통근)로 이 사례는 해결됐다** — `1999-12-09 22:12` 이 `약간 신강` 으로 나온다.
그 뒤에도 실측에서 어긋나는 사주가 남는지 보고 착수 여부를 판단한다. 근거 없이 관례를
늘리지 않기 위한 순서다.

→ 완료 기준: 착수 시 정한다. 최소한 위 조건 목록 각각에 대해 어느 쪽을 택했는지와
그것이 고전인지 우리 관례인지를 `docs/saju-validation.md` 가 밝혀야 한다.

### [TASK-30] 유형을 먼저 고르는 두 단계 플로우 · **(O)** · ⬜ 대기

지금은 한 화면에 이름·생년월일·시각·유형·고급설정이 전부 있고 **유형 버튼이 폼 중간**에
있다. 처음 온 사람은 무엇을 받게 되는지 모른 채 생년월일부터 넣는다. forceteller 처럼
**① 무엇을 볼지 고르고 → ② 그 다음에 정보를 넣는** 순서로 바꾼다.

```
/                     유형 선택 (카드 3장, 서버 컴포넌트·정적)
  └─ /reading/[type]  입력 + 결과   ← 입력값은 이동해도 남는다
```

#### 결정 1 — 단계는 클라이언트 상태가 아니라 **라우트**로 나눈다

ⓐ 뒤로가기가 그대로 동작하고 ⓑ `/reading/diet` 를 바로 공유·북마크할 수 있으며
ⓒ 유형별 메타데이터를 붙일 자리가 생긴다(TASK-31). 클라이언트 스텝 상태로 하면 셋 다 잃는다.

- **세그먼트 값은 기존 `ReadingType` id 를 그대로 쓴다** (`general`·`diet`·`yearly`).
  한글 슬러그를 따로 만들면 API 계약(`schema.ts`)과 URL 이 두 벌이 된다.
- `generateStaticParams` 로 `READING_TYPES` 를 프리렌더하고, 그 밖의 값은 `notFound()`.
- 카드는 버튼 + `router.push` 가 아니라 **`next/link`** 여야 새 탭·가운데 클릭·크롤러가
  다 동작한다.

#### 결정 2 — 입력값은 이동 사이에 **유지하되 저장하지 않는다**

한 번 넣은 생년월일을 유형 바꿀 때마다 다시 넣게 하면 단계를 나눈 이득이 마찰로 상쇄된다.
그렇다고 저장하면 개인정보 처리방침이 무너진다. **메모리에만 두면 둘 다 피한다.**

- **폼 상태를 `app/layout.tsx` 의 클라이언트 프로바이더로 올린다.** Next 16 문서가
  "layouts preserve state, remain interactive, and do not re-render on navigation"
  (`node_modules/next/dist/docs/01-app/04-glossary.md`)을 보장하므로 루트 레이아웃의
  React state 는 `/` ↔ `/reading/*` 이동에서 살아남는다. **`app/reading/layout.tsx` 는
  안 된다** — `/`(유형 선택)를 거쳐 가면 언마운트되어 값이 날아간다.
- **`sessionStorage`·`localStorage`·쿼리스트링은 쓰지 않는다.** 셋 다 생년월일이 프로세스
  밖으로 나간다 — 앞의 둘은 디스크에, 쿼리스트링은 방문 기록과 **Vercel 액세스 로그**에.
  `app/privacy/page.tsx` 의 "저장하지 않습니다" 를 고쳐야 하는 쪽으로 넘어간다.
- 메모리 상태는 **지금 폼이 이미 하는 것과 같은 범주**다. 새로고침·새 탭·탭 닫기로 사라진다.
  그래서 **처리방침을 손대지 않아도 된다** — 이 조건을 벗어나면 고쳐야 한다는 뜻이기도 하다.
- 프로바이더는 클라이언트 컴포넌트라 `components/` 에 둔다 (`lib/` 의 `server-only` 규칙과
  섞지 말 것). `children` 을 prop 으로 받으므로 `/` 는 여전히 서버 컴포넌트로 렌더된다.
- **보존 대상은 입력값뿐이다.** 원국·풀이(`chart`·`reading`)는 유형마다 다르므로 들고
  다니지 않고, 유형을 옮길 때 진행 중인 스트림은 `abort` 한다.

#### 작업

- [ ] `lib/saju/schema.ts` 의 `READING_TYPE_LABEL` 옆에 `READING_TYPE_DESCRIPTION`
      (카드 한 줄 설명)을 **`Record<ReadingType, string>`** 으로 추가한다.
      삼항·인덱스 시그니처로 두지 말 것 — 유형을 늘릴 때 컴파일 오류로 잡히지 않는다.
- [ ] 입력값 프로바이더를 만들고 `app/layout.tsx` 에 끼운다.
- [ ] `SajuForm` 이 로컬 `useState` 대신 프로바이더를 읽고 쓰게 한다.
- [ ] `/` 를 유형 선택 화면으로 바꾼다 (`READING_TYPES` 순회 + 카드 3장).
- [ ] `app/reading/[type]/page.tsx` 를 만들고 `SajuForm` 에 `readingType` 을 **prop 으로**
      넘긴다. 폼 안의 `readingType` state 와 "풀이 유형" fieldset 은 제거한다 —
      두 곳에서 고를 수 있으면 반드시 어긋난다.
- [ ] `resultType` state 를 정리한다. 유형이 라우트에서 오면 생성 중에 바뀔 수 없으므로
      `ResultView` 에 `readingType` 을 그대로 넘기면 된다.
- [ ] **값이 이미 있으면 폼을 접고 요약 한 줄 + "수정" 만 보여준다**
      (`1999-12-09 · 22:12 · 여성` 처럼). 첫 방문은 펼친 폼 그대로.
      접힌 상태에서 **바로 제출**할 수 있어야 한다 — 유형만 바꿔 다시 받는 것이 두 번 클릭.
- [ ] 입력 화면 상단에 고른 유형을 표시하고 `/` 로 돌아가는 링크를 둔다.
- [ ] `FirstVisitNotice` 를 입력 화면으로 옮긴다. "입력한 생년월일은 저장하지 않습니다" 는
      **정보를 넣기 직전에** 보여야 뜻이 있다. 옮기면 `/` 는 클라이언트 컴포넌트가 없어진다.
- [ ] 테스트: `READING_TYPES` 순회로 ⓐ 세 유형 모두 설명이 있고 서로 다른지
      ⓑ 설명 문구가 금지 어휘를 안 쓰는지 확인한다 (`diet` 는 처방·수치,
      `yearly` 는 예언 어휘 — `constitution.test.ts`·`yearly.test.ts` 의 목록을 재사용).
- [ ] `CLAUDE.md` 를 같은 커밋에서 갱신한다 — 아키텍처 그림의 진입점, "섹션 계약" 절의
      `resultType` 문단(이제 라우트가 유형을 정하므로), 그리고 **결정 2 를 규칙으로** 남긴다
      (입력값은 메모리에만 — 저장소·URL 로 옮기면 처리방침을 고쳐야 한다).

→ 완료 기준: `/` 에 생년월일 입력이 없고, 카드를 눌러야 입력 화면이 나오며, 그 화면에는
유형 선택 컨트롤이 없다. 세 유형 모두 `/reading/{type}` 직접 접근으로 동작하고 잘못된
세그먼트는 404 다. **유형을 바꿔도 입력이 남아 있고 새로고침하면 비어 있으며,
브라우저 저장소·URL 어디에도 생년월일이 없다.** `npm run lint` · `typecheck` · `test` · `build` 통과.

### [TASK-31] 유형별 문구·메타데이터와 결과 뒤 동선 · **(S)** · ⬜ 대기

TASK-30 이 뼈대를 세운 뒤 살을 붙인다. **순서가 이 방향인 이유**: 라우트가 생기기 전에는
`generateMetadata` 를 붙일 자리가 없고, 유형별 카피를 먼저 쓰면 화면 없이 문구만 고치게 된다.

- [ ] `/reading/[type]` 에 `generateMetadata` 로 유형별 title·description 을 붙인다.
- [ ] **og:image 는 유형별로 만들지 않는다.** 고정 카드(`app/opengraph-image.png`) 하나를
      유지한다 — 세 벌이 되면 `docs/og-card.html` 원본도 세 벌이고 팔레트 검사
      (`lib/design/tokens.test.ts`)도 그만큼 늘어난다. 얻는 것보다 유지 비용이 크다.
- [ ] 입력 화면 헤더 문구를 유형에 맞게 바꾼다 (지금 `app/page.tsx` 의 문구는 종합 풀이 기준).
- [ ] 결과 아래에 나머지 두 유형으로 가는 링크를 넣는다 (`/reading/{다른 유형}`).

  **`router.replace` 로 URL 과 화면을 따로 맞추는 편법을 쓰지 않는다.** TASK-30 의
  프로바이더가 입력을 들고 있으므로 평범한 라우트 이동으로 충분하다 — 옮겨 간 화면은
  값이 채워진 채 접혀 있고, 제출 한 번이면 다른 유형의 풀이가 나온다. URL 과 보이는
  결과가 항상 일치하는 쪽을 택하는 것이다.

→ 완료 기준: 세 유형의 `/reading/{type}` 이 서로 다른 title·description 으로 나오고,
결과를 받은 뒤 다른 유형으로 두 번 클릭에 넘어갈 수 있으며 그때 생년월일을 다시 넣지 않는다.
